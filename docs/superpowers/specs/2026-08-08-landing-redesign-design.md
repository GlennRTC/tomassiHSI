# tomassiHSI landing page redesign — design spec

Date: 2026-08-08 (updated same day after first build + review pass)
Scope: visual/structural redesign of `tomassi-hsi-mockup.html`. No code in this doc — this defines what gets built, not the build itself.

**Status: superseded by a full brand pivot.** Section 4 below reflects the "Editorial Minimal" direction as originally approved and built; §4.5, §8, §9 are revisions made to that direction. **§10 below replaces the entire visual/brand system (Editorial Minimal → Carbon Light) and is authoritative wherever it conflicts with anything above it**, including the palette, typography, architecture, and non-goals in §2–§6. §9's content policy (real, verified project data — no fabrication) is the one thing that carries forward unchanged; §10 explains how.

## 1. Problem

The current mockup (narrow single-column wrap, serif/mono mix, numbered service list, HL7-segment eyebrow, AHA-style case list) is professional but reads as generic "clean minimal SaaS template." It needs personality specific to Glenn as an integration developer — visible in structure and detail, not loud graphics — without:

1. The oversized-headline / centered-hero SaaS look
2. Gradient cards with rounded corners
3. Anything playful/cute that undermines trust with non-technical buyers (lab directors, clinic owners)

Existing brand system stays fixed: primary blue `#0B5C8C`, amber signal `#B45309`, ink `#132537`; serif headings (Iowan Old Style/Palatino), sans body, IBM Plex Mono for technical/data labels; the HL7 segment-syntax "protocol header" motif for section labels.

## 2. Reference calibration

Four references were used to calibrate taste, not to copy:

- **iconplc.com** — editorial minimalism, generous whitespace, orange accent, stat call-outs, section-label hierarchy. This is the **dominant register**.
- **ehr.meditech.com** — not a visual reference; the useful lesson is **information density & structure**: distribute credibility signals (stats, dates, status) next to the section they support, rather than siloing them in one hero strip.
- **monolayer.dev** — terminal command blocks, numbered sequential steps, technical artifacts treated as real tooling rather than illustration. Used only for its *structural device* (a log/rail treatment), not its dark/playful tone.
- **idealista.com** — dense, consistent tag/metadata chips attached to every listing. Used as a component pattern (key::value chips), applied sparingly.
- The "pixel-like font" reference (idealista/monolayer) is already satisfied by the existing IBM Plex Mono system — no new typeface needed.

## 3. Cross-cutting principle (applies everywhere)

Regardless of section, distribute credibility signals (stats, dates, status) near the content they support instead of collecting them into one hero stat strip. Give every section a consistent, scannable label grammar. This is an information-architecture fix inherited from the Meditech reference, not a stylistic choice — it applies to all sections below.

## 4. Chosen direction: Editorial Minimal (primary) + Functional Ledger accent + Interface Log in Casos

### 4.1 Primary structure — Editorial Minimal

**Thesis:** a trade-publication layout — disciplined type hierarchy, generous whitespace, amber used as the single sparing "signal" color, technical detail confined to small structural tags.

- **Grid:** replace the single centered 760px `.wrap` with a real asymmetric two-column grid at desktop (~35/65 split). Section labels live in a left margin column (like a magazine running header); content flows in the right column. This is what makes the layout "engineered, not centered" — the asymmetry is load-bearing, not cosmetic.
- **Protocol-header evolution:** the current hero-only eyebrow (`MSH|^~&|...`) becomes a repeating margin marker present at *every* section, not just the hero — same segment-syntax device, consistently applied. Typography stays quiet (small, `--ink-mute`, mono) so it never outweighs the serif heading beside it.
- **Signature detail (second-look):** a small static tag near the footer (and optionally near major sections), styled like a git short-hash — e.g. `rev. a3f9c1`. Reads as an ordinary build/version tag to anyone; means slightly more to a visitor who recognizes the convention. No JS needed — a static string is enough, since the page has no build step to hash against.
- **Mobile:** the 35/65 grid collapses to single column; margin labels move above their section content (current mobile behavior for existing labels, unchanged in spirit).

### 4.2 Accent — Functional Ledger chip component

Introduce one reusable `key::value` chip component (mono, small, quiet border) mimicking HL7 field syntax as functional content. Used **sparingly** — only on the 3 case items and the stat strip — never on every line, so it stays a texture, not a spec sheet. Example: `STATUS:: EN PRODUCCIÓN` `DESDE:: 2025`.

### 4.3 Casos section — Interface Log treatment

The Casos section gets the log/rail treatment (from the "Interface Log" direction), because its content already carries real dates and reads naturally as production history rather than marketing copy.

- A narrow mono rail (sequential line numbers, small and muted) runs beside the case list, echoing a log viewer.
- Each case row is a single grid container spanning both the rail number and the case content, so `:hover` on the row highlights both — pure CSS, no JS required.
- The existing `case-tag` / `case-meta` mono styling stays; the `key::value` chip from 4.2 can appear here too (e.g. status), reusing the same component rather than inventing a second one.

### 4.4 Anti-pattern check

- No oversized centered hero — the asymmetric grid breaks that read from the top of the page.
- No gradients or rounded cards — the chip and rail components are flat, bordered, monospace.
- Alienation risk is kept low by scoping jargon-as-structure to the margin labels, the Casos rail, and sparse chips — all quiet, small, and secondary to the plain-Spanish headings and prose, which remain the primary reading path.

### 4.5 Revisions after first build

The first build (Editorial Minimal + protocol-header margin markers + Interface Log rail) read as "too plain, like a minimalist blog" once rendered. Two rounds of direct feedback changed the direction:

1. **Card system added.** Servicios, Enfoque, and Casos moved from flat bordered-row lists to a `.card` / `.card-grid` component (white background, 1px border, 6px radius, subtle shadow that deepens on hover, 3-column grid collapsing to 2 then 1). Modeled on how ehr.meditech.com groups testimonials/customers/resources into card grids — confirmed by fetching that page, not just inferred. The stat strip (10+ años / 3 países / HL7·FHIR) came back as a 3-card row directly under the hero instead of being fully dispersed per §3 — the dispersal principle was in tension with wanting an immediate visual break after the hero, and the card row won. The Casos Interface Log rail (sequential line-number rail + row-hover sync) was **dropped**, replaced by case cards; the rail's row-hover mechanism doesn't fit inside a card grid, and the card treatment already gives each case its own contained, scannable unit — the log rail was a hero for a section it no longer occupies.
2. **Protocol-header device removed entirely.** The repeating margin-column `MSH|`/`OBR|`/`EVN|`/`OBX|`/`PID|`/`MSA|` segment strings (§4.1) were cut — Glenn didn't like them. The `.margin-col` / `.section-grid` asymmetric layout stays (it still holds each section's `.section-label`), but the hero no longer uses the two-column split since removing its protocol line left the margin column empty — hero now sits in a plain `.wrap`.

Kept as originally specified: brand colors/type, the `key::value` chip component (still used for case STATUS chips and the Sobre mí experience chip), the asymmetric margin/content grid for non-hero sections, the Technics/Consultancy service split, no JS, no new dependencies, `rev. 2026-08-08` as a real (not placeholder) last-updated tag near the footer contact card.

3. **Amber accent added, scoped to one place.** `--signal`/`--signal-dim` (defined since the original brand system but unused in the build) now drive a `.chip.status-live` variant: case cards with `STATUS:: EN PRODUCCIÓN` get an amber-tinted chip, `COMPLETADO` stays neutral — color reinforces a real state distinction rather than decorating. Text color for the live chip is `#8F4207`, darkened from the raw `--signal` token because `--signal` only cleared ~4.0:1 against `--signal-dim`, short of the 4.5:1 AA minimum needed at that size.
4. **Accessibility fixes from a `/ui-ux-pro-max` review:** `--ink-mute` darkened from `#8B98A5` to `#5F6B75` (was 2.94:1 on white, now 5.46:1) and the extra `opacity:0.6` on `.case-log-num` removed (it was undermining the color fix); Enfoque's step headings changed from `h4` to `h3` to stop skipping a heading level after the section's `h2`; nav links moved into a real `<nav>`, and all main content wrapped in `<main>`.
5. **Layout borrowed from ehr.meditech.com's section pacing (colors/fonts untouched).** Per Glenn's direction — inspect Meditech's structure, keep tomassi's brand — three changes: (a) Casos moved up to sit directly after the stat strip, before Servicios, so proof-of-work appears earlier in the scroll (mirrors Meditech's nav→hero→testimonials→customer-stats pacing); nav link order updated to match. (b) Casos and Servicios got a `.dense` modifier (40px vertical padding vs. the default 56px) to create the alternating dense/sparse rhythm Meditech uses, instead of uniform section spacing throughout. (c) Footer gained a second column (`.footer-cols` / `.footer-links`) of in-page section shortcuts next to the contact card, echoing Meditech's multi-column footer — using real anchors, not invented links. Meditech's testimonials, client-logo grid, blog/news hub, and awards grid were **not** ported: replicating those would require real client quotes, press mentions, or certifications Glenn doesn't have yet, and fabricating them isn't an option.
6. **Per-section accent colors, researched against biotech/health-tech/clinical-data-flow palettes.** Glenn asked for sections to read as visually distinct via color. Added a `--accent`/`--accent-dim` token pair (defaults to `--primary`/`--primary-dim` at `:root`) that section-scoped components — `.section-label`, `.track-label`, `.service-num`, `.service .tag`, `.step-marker`, `.case-tag`, `.chip .v` — reference instead of the hardcoded primary blue. Two new hues were added and scoped by section selector: `#casos{--accent:var(--teal)}` (`#0B6B76`, "flujo de datos" / production systems — chosen since Casos is literally live case data), `#enfoque, section.about{--accent:var(--green)}` (`#1B7A43`, biotech/clinical association for methodology and the personal-bio section). Hero, stat strip, Servicios, and Contacto keep the default blue `--accent` — Servicios because data-interoperability is blue's original association, Hero/Contacto because the page needs one color that bookends open and close. All new hues checked for 4.5:1 text contrast on white and on their `-dim` tint before use (teal 6.22:1 / 5.37:1 on tint, green 5.37:1 / 4.69:1 on tint). The amber `status-live` chip (§ above) is untouched by this — it's a state signal, not a section identity, and stays amber regardless of which section it appears in.
7. **Servicios rebuilt as a side-by-side UML-style diagram, with a first (minimal) JS addition.** Glenn asked for Technics/Consultancy to sit side by side and read like a UML diagram, with some animation. Replaced the two stacked `.card-grid` lists with `.uml-diagram`: two `.uml-box` panels (sharp 2px corners, solid `--ink` border, a filled `--accent` header compartment reading "Technics"/"Consultancy") divided into `.uml-row` entries — deliberately stopping short of literal UML notation (no `+`/`-` visibility marks, no type signatures) since the original spec's anti-pattern list rules out anything that could alienate non-technical buyers (lab directors, clinic owners); the box-with-compartments silhouette alone reads as "diagram" without demanding UML literacy. An animated SVG connector line (`.uml-link`, with a small circle at its midpoint) sits between the two boxes, mirroring a UML association. Animation is vanilla JS — the project has carried no JS until now, but the spec's non-goals always allowed it "if used anywhere, minimum needed, KISS." A single `IntersectionObserver` (~15 lines, no dependencies) adds `.in-view` to each `.uml-row` and to `.uml-link` on scroll-into-view; CSS transitions handle the actual motion (row fade/slide, staggered 80ms per row; connector line drawn via `stroke-dashoffset`). Three fallbacks guard against it ever hiding content: browsers without `IntersectionObserver` get `.in-view` added immediately; a `prefers-reduced-motion` media query zeroes out all transitions and forces the visible end-state; and a `<noscript>` block forces the same end-state if JS is disabled entirely. Collapses to a single stacked column with the connector hidden below 760px.
8. **Clarified to actual section backgrounds (not just accent details), plus a type-system upgrade.** Glenn's first color ask (#6 above) was interpreted as label/marker accents; he clarified he meant full section backgrounds. Applied the existing `-dim` tokens as literal `background` on the section itself — `#casos{background:var(--teal-dim)}`, `#servicios{background:var(--primary-dim)}`, `#enfoque{background:var(--green-dim)}` — while `.card` stays hardcoded white, so cards read as raised panels against their section's tint (mirrors how the researched palettes themselves pair a near-white `Card` color against a soft tinted `Background`, e.g. Patient Portal's `#FFFFFF` card on `#F0F9FF` background). Hero, stat strip, Sobre mí, and Contacto stay unthemed/white so the sequence alternates instead of every section being colored — Sobre mí deliberately keeps its green *accent* (label, chip) without a green *background*, so it doesn't visually merge into the adjacent green Enfoque section above it. Confirmed ink text stays ≥13:1 and ink-dim ≥5.7:1 against all three new backgrounds — no contrast regression from the tinting. Separately, typography moved from system-font stack + an unloaded "IBM Plex Mono" reference (no `<link>` existed, so almost no visitor ever actually saw Plex Mono — it silently fell back to their OS mono font) to the full IBM Plex superfamily, loaded via Google Fonts `<link>` in `<head>`: `--serif` → IBM Plex Serif, `--sans` → IBM Plex Sans, `--mono` → IBM Plex Mono (now actually loads). Chosen over an "Editorial Newsroom" (Newsreader + Public Sans) alternative Glenn was also shown — Plex was picked to read as one deliberately-designed type system across headings/body/labels rather than a stitched-together pairing, and to avoid the Inter/Poppins/Playfair Display/JetBrains-Mono cluster that dominates AI-generated and template sites. The two inline SVG wordmarks (header + footer) were updated to match.

9. **Declined a font request on licensing + brand-fit grounds, sized up instead.** Glenn asked to use "Determination" (dafont.com) for section labels and the H1. Checked the license: the author states "for personal use only" — this page runs a paid-consulting CTA and contact funnel, which is commercial use under that license, so it wasn't used regardless of Glenn's initial "it's my personal brand page" framing. It's also Undertale's dialogue bitmap font — a hard clash with the anti-playful, non-technical-buyer-trust register this spec set out from the start (§1). Declined, offered two brand-safe alternatives (size up existing IBM Plex, or source a commercially-licensed distinctive display font); Glenn didn't pick, so applied the lower-risk default: `.section-label` grew `11px→14px` and gained `font-weight:600`; hero `h1` grew from a `clamp(32px,5vw,48px)` ceiling to `clamp(36px,6vw,58px)` with tightened line-height. Same IBM Plex Serif/Mono already in use — no new font risk introduced.
10. **Enfoque expanded from 3 cards into a 6-node vertical flowchart, then rebuilt again as a zigzag milestone diagram.** Glenn wanted the process section to read as a more granular PM-style flowchart. First pass: the existing 3 phases were unpacked into 6 stages by splitting their own existing sentences into discrete steps (no invented claims) — Kickoff y relevamiento → Diagnóstico técnico → Diseño de la interfaz → Plan de pruebas → Implementación → Estabilización y monitoreo — shown as a vertical sequence of numbered circles joined by a straight connector. Glenn then linked a reference image: a horizontal "line flow infographic" with alternating up/down diamonds, a numbered badge per diamond, an icon inside each, and a connecting line. Rebuilt to match that structure, with one deliberate substitution: the reference used a different rainbow color per step; that was **not** ported, since it would have broken the one-accent-per-section discipline built in item #6/#8 above — all six diamonds, the number badges, and the connector use the section's single green `--accent` instead. Structure: `.flow-diagram` holds an absolutely-positioned `<svg class="flow-path">` (viewBox `0 0 600 280`, `preserveAspectRatio="none"` so it stretches horizontally while its height stays pixel-matched to the row) with one zigzag `<polyline>`, plus a `.flow-row` of 6 `.flow-node.up`/`.down` items — each a CSS diamond (rotated-45° square, icon counter-rotated back to upright) with an absolutely-positioned circular number badge, sitting above a short label. Six hand-authored inline SVG icons (stroke, `currentColor`, matching the existing nav-icon convention — no icon library) pick out one per stage: message bubble, magnifying glass, connected nodes, checklist, launch arrow, pulse line. Reveal mechanics changed from per-step to whole-diagram: a single `IntersectionObserver` target (`.flow-diagram`, added to the same observer array as `.uml-row`/`.uml-link`) toggles `.in-view`, and `.flow-node`/`.flow-path polyline` react to that parent class via CSS — six individual triggers weren't needed since the whole row enters view together at this width. **Mobile fallback (below 860px):** since a horizontal zigzag can't fit a narrow viewport without forcing scroll (a hard anti-pattern per the UX priority table), the SVG path is hidden, the row switches to `flex-direction:column`, the up/down offset is cancelled, and each node lays out as an icon+label row — the same "hide the fancy connector, stack simply" fallback pattern already used for the Servicios UML diagram. `prefers-reduced-motion` and `<noscript>` fallbacks were updated to reference the new class names rather than duplicated. `.step`/`.step-marker`/`.flow-step`/`.flow-line` CSS from the two prior iterations was deleted rather than left dead.

## 8. Whole-page rearrange pass — "stop looking AI-generated" (post-launch revision)

Glenn asked for a full-page review specifically to identify what still read as generic/AI-template despite all prior customization, and to fix all of it. Diagnosis: the *macro skeleton* (Hero → 3 stat-cards → Features → Process → Cases → About → Contact) is the exact default order every landing-page generator produces, regardless of how custom the components inside each slot are. Two elements were the clearest tells:

1. **The hero** — headline + subhead + 2 buttons, floating alone with nothing beside it. The single most common AI-generated hero shape.
2. **The 3-stat-card strip directly under the hero** — the second most recognizable "generated site" pattern. This directly contradicted §3's original cross-cutting principle (distribute credibility signals near the content they support, don't collect them in one strip) — that principle got overridden earlier for a card-based visual break (§4.5 item 1) when the page still felt too plain; revisited now that the page has real visual texture elsewhere (UML diagram, custom SVG chart, per-section color).

Changes made:
- **Stat strip removed entirely.** Its 3 numbers redistributed to where they're actually relevant: "10+ años" / "3 países" moved into the hero's own margin-col as small serif-numeral annotations (`.hero-stat`) beside the headline — this simultaneously kills the "hero floats alone" problem and the "separate stats block" problem in one move. "HL7 · FHIR · ASTM · CDS Hooks" moved to a `.chip` next to the Servicios heading (protocols belong next to the section about technical services, not in a generic hero-adjacent strip).
- **Hero restructured** to use `.wrap.section-grid` (margin-col + content-col) like every other section, instead of being the one section that was just a bare `.wrap` — consistent grid language across the whole page now, and the margin-col annotations give it something beside the text.
- **Casos rebuilt from a 3-card grid into a ledger/log table** (`.log-table`/`.log-row`) — monospace row layout (number · tag+title · status dot · period), row-hover highlight. Cards were the one generic "feature-grid" pattern left in a section that is literally a list of dated production deployments — a log/ledger reads as exactly what it is, and is a genuinely different visual language from every other component on the page (UML boxes, project chart, cards), not a fourth variation on "put it in a bordered box."
- **Sobre mí de-carded.** Was the last plain "text in a `.card`" — this section is a personal bio, not a spec sheet, so it deliberately does *not* get a card now: a serif pull-quote-style lead statement, a scannable `.tag` list for the technology stack (reusing the same `.tag` component now shared with Servicios instead of being buried in prose), and a short closing note. The redundant `EXPERIENCIA:: 10+ AÑOS` chip was dropped since that number now lives in the hero.
- **`.tag` refactored to a shared base class** (was scoped `.uml-row .tag` only) so Sobre mí's tag list reuses it instead of duplicating the rule — one component, two call sites.
- Section order was reconsidered but left as-is (Hero → Casos → Servicios → Enfoque → Sobre mí → Contacto) — the Casos-before-Servicios proof-early ordering was already a deliberate earlier decision (§4.5 item 5) and still holds.

## 10. Full pivot — "Carbon Light" direction (supersedes §§2–6, 8)

Glenn commissioned a project brief (`docs/superpowers/specs/tomassi_hsi_project_brief_prd.md`) and a Google Stitch prototype (`stitch_tomassi_hsi_systems_integration/`: `code.html`, `DESIGN.md`, `screen.png`) independently of this spec's iteration history. Reviewed together, they describe a different brand system — not a further revision of Editorial Minimal but a replacement of it. This section is that replacement; §2–§6 and §8 (palette, typography, grid, chip component, per-section accent colors, protocol-header motif, stat-strip placement) are historical record of a direction no longer being built. §9's content policy — real, verified project data, no fabrication — is the one constant and is restated below in its new home.

**Source-material conflict, resolved:** the PRD names the system "Carbon Light" (white background, orange signal). `DESIGN.md`'s frontmatter, titled "Carbon Engineering," specifies a *dark* palette (`surface #131313`). But `code.html` doesn't use that palette — it defines its own light Tailwind theme (`surface #ffffff`, `on-surface #111827`), and `screen.png` confirms the page renders light. Decision: **light theme, per code.html/screen.png** — `DESIGN.md`'s dark tokens are a reference document that was never actually applied and are not part of the target.

### 10.1 Brand system

- **Color:** single accent, Signal Orange `#FF6B00`, used for CTAs, active nav state, hover accents, and status pips. No blue, no amber, no per-section hues — the multi-hue system built in §4.5 item 6 is dropped along with the section-tinted backgrounds from §4.5 item 8.
- **Background:** white, with a subtle repeating linear-gradient grid (`.grid-bg`, 32px cells, `#f3f4f6` lines) on the hero and Servicios sections — a technical-blueprint texture, not a color block.
- **Typography:** JetBrains Mono only, for headings, labels, and body copy alike. Replaces the IBM Plex Serif/Sans/Mono three-way system from §4.5 item 8 entirely — there is no serif in this direction.
- **Shape:** every component — buttons, cards, inputs, tags, badges — is `0px` border-radius. No shadows for elevation except a subtle `shadow-sm` on cards; hierarchy comes from 1px solid borders (`#e5e7eb`) and background-tone steps (`surface` / `surface-low` / `surface-high` / `surface-highest`), matching `DESIGN.md`'s "Flat Depth / Structural Outlines" principle even though its color values weren't adopted.
- **Iconography:** Material Symbols Outlined (variable font), thin-stroke, used sparingly in the nav, section headers, and stat cards — replaces the hand-authored inline SVG icon set built for the Enfoque flowchart in §4.5 item 10 (that flowchart is itself dropped, see §10.3).

### 10.2 Architecture change (deviates from `CLAUDE.md`)

The mockup moves from the current hand-rolled system (CSS custom properties in `:root`, everything inline, zero dependencies) to the same stack the prototype uses: **Tailwind CSS via CDN script, Google Fonts (JetBrains Mono), and the Material Symbols Outlined web font.** This is a deliberate, confirmed deviation from `CLAUDE.md`'s current description of the project ("no build system... no framework... no JavaScript") — `CLAUDE.md` needs a follow-up update once this direction is implemented; not done as part of this spec.

Carried forward from the ponytail-review of `code.html` (see review notes from this session) — clean these up while porting rather than copying them in:
- Collapse the Tailwind `fontFamily` config from 8 duplicate keys (all mapped to `["JetBrains Mono"]`) to one.
- Drop unused config: `spacing.unit`, `colors.on-primary-container`, `colors.surface-high` — none are referenced by any class.
